# Metadata review and library browsing

The Suggestions tab combines a file-oriented editor with a per-song replacement chooser. Browse roots and folders from the indexed library or switch to song search. Select a file to edit individual fields, save proposals, and review them through **Choose suggested metadata**. Unsaved edits must be saved or discarded before another file can replace the editor’s draft. Accepted catalog overrides continue to survive rescans; restoring an extracted field removes its override.

**Review changes** groups loaded suggestions by song. Opening **Choose metadata** fetches every pending candidate for that song, including candidates beyond the review list’s loaded page. Each field defaults to keeping its current value. Choose a proposed source, optionally edit its text, and compare current/proposed artwork before applying selected fields. Blank optional fields are valid; clearing Album classifies a song as Single. Applying replacements accepts the selected candidates and dismisses competing candidates for the same fields. Fields kept current remain pending. **Bulk accept by field** retains the existing newest-candidate behavior and explicitly includes unpaged suggestions.

Replacements are atomic. Each selected candidate must still be pending, belong to the selected accessible song, and represent a distinct field. The compared current values must still match after the track is locked. A stale comparison, invalid edit, or conflicting choice prevents the entire update; the chooser retains selections for retry or offers a reload. Edited proposals record the final accepted value and administrator edit attribution. The API enforces administrator/session/CSRF checks, validates edited values, and prevents arbitrary artwork-path replacement.

Folder browsing follows catalog paths and lists immediate children with pagination. It does not enumerate arbitrary filesystem directories or change music files. Unavailable/excluded tracks do not contribute files, folder counts, or roots. Windows catalog separators are normalized for navigation. Empty folders and unindexed non-audio files are absent. Source names and filenames are displayed as plain text.

## Reference implementation review

Stash’s [ScrapeDialogRow](https://github.com/stashapp/stash/blob/develop/ui/v2.5/src/components/Shared/ScrapeDialog/ScrapeDialogRow.tsx) compares original and scraped values, selects which value to use per field, and exposes editable replacement inputs and image comparisons. Its [ScrapeDialog](https://github.com/stashapp/stash/blob/develop/ui/v2.5/src/components/Shared/ScrapeDialog/ScrapeDialog.tsx) gathers the selections behind Apply/Cancel. We adapted the interaction to pending music-library suggestions: a source selector handles competing candidates, and replacements use our catalog transaction rather than Stash’s entity/scraping model.

Jellyfin’s [directory browser](https://github.com/jellyfin/jellyfin-web/blob/master/src/components/directorybrowser/directorybrowser.js) separates file/directory entries, navigates through parents, and delegates file selection. Its [metadata editor](https://github.com/jellyfin/jellyfin-web/blob/master/src/components/metadataEditor/metadataEditor.js) loads a selected item, edits individual fields, and submits updates with metadata locking information. The corresponding server [EnvironmentController](https://github.com/jellyfin/jellyfin/blob/master/Jellyfin.Api/Controllers/EnvironmentController.cs) exposes directory/path operations, while [ItemUpdateController](https://github.com/jellyfin/jellyfin/blob/master/Jellyfin.Api/Controllers/ItemUpdateController.cs) handles metadata updates. We use breadcrumbs and selected-file field editing, backed by our permission-filtered index and existing persistent overrides.

These references informed the interaction design. The implementation is original TypeScript/Go/CSS using Cadence’s existing shadcn/Radix components; no source code or assets from either project were incorporated.
